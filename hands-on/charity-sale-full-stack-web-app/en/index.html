[Hands-on] Building a Full-Stack Charity Sale App

A concise record of the motivation, online architecture, technology choices, and key takeaways behind a simple charity-sale project.

01

Motivation

A while ago, a friend planned to sell a large number of unused items at discounted prices and donate the proceeds to children in underserved mountain communities. They created a group chat, posted photos there, and buyers and sellers placed orders by sending messages. The conversation quickly became cluttered and difficult to track. Wanting to support the charitable effort, I helped my friend build a simple online charity-sale registration system.

The event did not need a complete e-commerce platform. It needed sellers to list items quickly, buyers to see availability clearly, and fulfillment staff to connect each purchase with delivery information.

Fast listing

One image plus a name, price, category, and description.

Clear browsing

Filter available and sold items instead of searching through chat history.

No double-selling

Only one concurrent buyer can successfully purchase an item.

Private delivery details

Names, phone numbers, and addresses remain internal.

02

Online architecture

Cloudflare Pages

Hosts the HTML, CSS, and JavaScript for buyer and seller interfaces.

Cloudflare Pages Functions

Provides /api/* for login, products, purchases, and orders.

Supabase Postgres

Stores product state, order numbers, and delivery fields with transactional consistency.

Supabase Storage

Stores product images while the database keeps public URLs.

What I used—and did not use

ChoiceReason
Vanilla HTML / CSS / JavaScript
No React or Vue		The interface is small and needs no build pipeline.
Cloudflare Pages Functions
No long-running server		Request-based execution suits a short, small event.
Postgres + Storage
Images are not stored in the database		Structured records and large files use appropriate storage.
Five-second polling
No WebSocket		Changes are infrequent; simple reliability matters more than absolute real time.
Shared seller password
No account system		Sufficient for a small event, not for fine-grained authorization or auditing.
Two critical rules

The public product API omits names, phone numbers, and addresses. A PostgreSQL atomic function and row lock ensure that an item can be sold only once.

04

Key takeaways

Define state first

Once available → sold is clear, seller, buyer, and order responsibilities follow naturally.

Put rules in the right layer

The UI handles experience, Functions enforce access boundaries, and the database ensures consistency.

Simplicity is a trade-off

Frameworks, WebSockets, and account systems can be omitted only when the limits are explicit.

Enforce privacy at the API

The browser should never receive data it does not need—not merely hide it in the interface.

What this practice demonstratesThis small project covers a complete online path from product flow and state modeling to serverless APIs, databases, object storage, privacy, and concurrency control.
